# MASTER PROMPT — TEXTILE HRM PROTOTYPE REWORK (PUBLIC-FIRST, GOVERNMENT-READY)

You are working on the Textile Institution Management System prototype for the Ministry of Textiles and Jute, Bangladesh.

Your task is to create a NEW set of design prototype options based on the instructions below.

This is NOT a generic SaaS dashboard project.
This is a Bangladesh government-level digital platform.
It must feel official, practical, clear, public-service-oriented, and easy for different user roles to operate.

The previous variations are not fully aligned with stakeholder expectations.
You must now produce a revised set of prototype options based on the following design baseline and product rules.

## 2. PRODUCT POSITIONING
This system should not be framed as only an HRM system.

Present it as:
Textile Institution Management System
or
Integrated Textile Institution Management Platform

Core story:
A centralized digital platform that connects textile institutions with the Ministry, while public users receive information and services and internal users work through role-based portals.

The platform must communicate:
- one connected ecosystem;
- one source of truth;
- institutional visibility from Ministry level down to institution level;
- public information + public services;
- role-based internal workflows;
- easier monitoring, approvals, reporting, and service delivery.

## 3. MAIN DESIGN CORRECTION
The landing page must be a real public website.
It must NOT look like a dashboard homepage.

The public landing page should feel closer in spirit to:
- IPEMIS public website
- Invest Bangladesh landing structure
- BIDA QuickServ service orientation

That means:
- bigger typography;
- strong hero banner with image;
- clean public navigation;
- public information sections;
- icon/illustration-supported sections;
- about section;
- notices;
- photo gallery;
- help/support;
- admissions information;
- public dashboard preview inside a section, NOT as a navbar item.

### Hero banner requirements
- large image banner
- strong headline
- short descriptive subtext

### Notice section requirements

Use tabs, chips, or categorized notice blocks.

## 7. LOGIN AND DOMAIN / PORTAL LOGIC
Do NOT present all roles as if they log in from the same visible public portal in the same way.

### Public website login should support:
- Admission Candidate Login
- Student Login
- Teacher Login

### Dedicated internal portals / domains should exist for:
- Ministry Portal
- Division Portal
- District Portal
- Principal / Institution Admin Portal

These can be represented in prototype as:
- separate login entry points,
- or a portal selector,
- or distinct domain indicators.

But the public main website should not openly behave like a giant common portal for every government role.

### Candidate lifecycle rule
Admission candidates may log in with temporary application / candidate ID.
If selected and finally admitted, candidate account transitions into student identity / student ID.

## 11. EDGE CASES THE FLOWS MUST CONSIDER
The prototype must not show only happy paths. Represent edge cases through status cards, alerts, placeholders, or sample states.

Examples:
- candidate application incomplete
- missing documents
- payment pending
- candidate selected but admission not completed
- candidate becomes student
- no class assigned yet
- attendance not yet submitted
- result pending publication
- service request returned for correction
- no notices in category
- no data available for a role
- user has no institution assigned
- approval pending with another level
- rejected / correction-required / completed states
